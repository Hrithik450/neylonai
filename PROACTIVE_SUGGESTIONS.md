# Proactive Suggestions — delivery rules

How launcher bubbles are paced, budgeted and generated. Update this file when
any of the numbers below change.

Code:

- Pacing + budget (client): `packages/sdk/src/react/proactive/use-proactive-suggestions.ts`
- Timing constants: `packages/sdk/src/react/proactive/config.ts`
- Session vs visitor storage: `packages/sdk/src/react/proactive/persistence.ts`
- Candidate generation (server): `packages/agent/src/agents/main-agent/proactive-suggestions/`

## Pacing

| Phase | Timing |
| --- | --- |
| First bubble of a session | `initialIdleMs` after the widget mounts |
| Bubble on screen | `displayMs` — 8s |
| Quiet gap before the next bubble | `rotateGapMs` + jitter — 10–12s |
| After the widget closes on a real chat | `postChatDelayMs` — 2s |

So a steady rotation is one bubble roughly every 18–20 seconds, never faster.

`minDisplayMs` / `minRotateGapMs` are enforced floors: a dashboard or stored
widget config may only make bubbles **rarer**, never more frequent. That keeps a
stale published config from reintroducing bubble spam.

A reload or SPA navigation does **not** restart the fast `initialIdleMs` path —
once anything has been shown in the session, the next bubble waits a full gap.

## Per-session budget

- **10 bubbles per session, welcome included.** After that the widget goes quiet
  for the rest of the session.
- A session is a tab session (`sessionStorage`). **Reloading re-enters the same
  session** and does not refund budget; a new tab starts a new session.
- The budget lives in `sessionStorage`, visitor history (`shownIds`,
  `hasVisitedBefore`) in `localStorage`, so tabs can't leak budget to each other.
- Suggestion ids are derived from the bubble text, so the same question can never
  reappear under a second id.

## On-demand bubbles (uncapped)

One **complete interaction** = the visitor opens the support widget, sends at
least one message, and closes it. Every completed interaction earns exactly one
freshly generated, deeply personalized bubble:

- It is **not** charged to the 10-bubble cap (`countsTowardSessionLimit` exempts
  `recent_conversation`).
- There is **no limit** on these — they keep coming after the cap is spent, one
  per interaction.
- It takes priority over any queued session bubble.
- The credit is persisted, so it survives a reload before delivery.
- Generated by `prompts.proactiveFollowUps` (exactly 1 suggestion) from the last
  8 messages; falls back to a deterministic topic follow-up if the model fails.

## Candidate quality

Bubble text comes from a ranked pool, best provenance first:

1. **Model-written candidates** — `generate-candidates.ts` asks the utility model
   (`gemini-3.1-flash-lite` via `getUtilityModel()`) for 12–14 bubbles grounded
   in that org's knowledge-base seeds and crawled page topics. Cached in Redis per
   organization + page for 6h, so it costs about one cheap call per page per
   window and never contains visitor data.
2. **Crawled page suggestions** — generated per section during the website crawl.
3. **Built-in page catalog** — hand-written per-path fallbacks.
4. **Deterministic seed/brand hooks** — template expansion, backfill only.

Every candidate passes `cleanQuestion` in `text.ts` (4–9 words, one trailing
emoji, no secrets, links or FAQ phrasing) before it can be shown.

Ranking is per visitor: page-path tokens, recent-conversation tokens (sent in
every mode, not just post-chat), a provenance bonus, a "catchiness" score, and a
stable per-visitor jitter so two visitors on the same page see different orders.
